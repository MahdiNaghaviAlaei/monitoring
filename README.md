# داشبورد مانیتورینگ سیستم‌ها و سرویس‌ها

پنل فارسی بر پایهٔ Laravel 12 و Filament 3 برای نمایش اطلاعات API مانیتورینگ: سلامت، CPU، RAM، دیسک، کانتینرها، لاگ و تاریخچهٔ مصرف منابع. این مخزن رابط Laravel است؛ سرویس جمع‌آوری متریک و Docker API باید جداگانه اجرا شود.

## پیش‌نیازها

- PHP 8.2 یا بالاترِ سازگار با composer.lock؛ Composer 2 و Git.
- افزونه‌های PHP موردنیاز Composer، به‌خصوص intl، mbstring، curl، dom، xml، fileinfo، openssl، PDO و pdo_sqlite. دستور composer check-platform-reqs وضعیت دقیق را بررسی می‌کند.
- دسترسی ماشین اجراکنندهٔ Laravel به API مانیتورینگ.
- برای پنل فعلی Node.js و Vite لازم نیست؛ دارایی‌های Filament با Composer منتشر می‌شوند و CSS مانیتورینگ مستقیم از public بارگذاری می‌شود.

## نصب و اجرا روی سیستم شخصی

دستورها را در ترمینال اجرا کنید. هنگام نصب اولیه برای دریافت وابستگی‌ها اینترنت لازم است:

```shell
git clone https://github.com/MahdiNaghaviAlaei/monitoring.git
cd monitoring
```

در PowerShell فایل تنظیمات را بسازید:

```powershell
Copy-Item .env.example .env
```

در Linux/macOS به‌جای دستور بالا از cp .env.example .env استفاده کنید. اگر .env از قبل وجود دارد آن را بازنویسی نکنید.

```shell
composer install
composer check-platform-reqs
php artisan key:generate
php -r "file_exists('database/database.sqlite') || touch('database/database.sqlite');"
php artisan migrate
php artisan make:filament-user
```

دستور آخر نام، ایمیل و رمز حساب ورود خودتان را می‌پرسد. هیچ حساب یا رمز آماده‌ای در مخزن قرار ندارد. SQLite برای کاربران، نشست‌ها و کش استفاده می‌شود؛ داده‌های مانیتورینگ از API دریافت می‌شوند.

در فایل .env آدرس واقعی API را تنظیم کنید؛ این آدرس نمونه است:

```ini
APP_ENV=local
APP_URL=http://127.0.0.1:8000
APP_LOCALE=fa
DB_CONNECTION=sqlite
SYSTEM_MONITOR_URL=http://127.0.0.1:8001
SYSTEM_MONITOR_PROTECTED_CONTAINERS=system_monitor
```

SYSTEM_MONITOR_URL باید ریشهٔ سرویس باشد، بدون /docs و بدون /api در انتها. نام کانتینر مانیتورینگ و وابستگی‌های ضروری آن را با کاما در SYSTEM_MONITOR_PROTECTED_CONTAINERS وارد کنید تا از داخل پنل متوقف یا راه‌اندازی مجدد نشوند.

```shell
php artisan config:clear
php artisan serve --host=127.0.0.1 --port=8000
```

ترمینال را باز نگه دارید و وارد http://127.0.0.1:8000/admin شوید. با حساب ساخته‌شده وارد شوید؛ صفحات سیستم‌ها و سرویس‌ها در منو هستند. نبود API مانع ورود به پنل نیست؛ ویجت‌ها وضعیت عدم دسترسی را نشان می‌دهند.

## آدرس API در Docker

آدرس باید از محل اجرای PHP قابل دسترسی باشد:

- Laravel روی میزبان و API در Docker: از پورت منتشرشده روی میزبان استفاده کنید؛ مثلاً http://127.0.0.1:8001.
- Laravel و API هر دو در یک شبکهٔ Docker: از نام سرویس و پورت داخلی آن استفاده کنید؛ مثلاً http://system-monitor:8000.
- API روی سرور دیگر: IP یا نام همان سرور و پورت قابل دسترسی در شبکه را وارد کنید.

این نام‌ها نمونه‌اند؛ نام و پورت واقعی را از تنظیمات Docker تیم بگیرید. داخل کانتینر، 127.0.0.1 به همان کانتینر اشاره می‌کند. پس از تغییر .env دستور php artisan config:clear را اجرا کنید.

## انتقال به سیستم بدون اینترنت

Clone به‌تنهایی وابستگی‌ها را همراه ندارد. روی سیستم متصل به اینترنت و با PHP/افزونه‌های سازگار با مقصد، composer install را اجرا کنید. سپس پروژه را همراه پوشهٔ vendor و دارایی‌های public به مقصد منتقل کنید. پوشهٔ vendor، فایل .env و دیتابیس محلی عمداً در Git نیستند.

روی مقصد .env را از .env.example بسازید، URL را تنظیم کنید، سپس مراحل key:generate، ساخت SQLite، migrate و make:filament-user بالا را انجام دهید. پوشه‌های storage و bootstrap/cache باید قابل نوشتن باشند. برای پروژه‌ای که قبلاً نصب شده، APP_KEY و دیتابیس موجود را حفظ کنید. پنل فعلی به npm install روی مقصد نیاز ندارد. در نصب آفلاین حتماً یک بار Network مرورگر را برای منابع خارجی بررسی کنید؛ تم یا فونت سفارشی مقصد ممکن است دارایی بیرونی داشته باشد.

برای ادغام در پروژهٔ موجود شرکت، کل .env و Provider آن پروژه را جایگزین نکنید؛ بخش انتقال فایل‌ها در ادامه را بخوانید.

## عیب‌یابی و تست

```shell
php artisan config:clear
php artisan view:clear
php artisan filament:clear-cached-components
php artisan route:list --path=admin
php vendor/phpunit/phpunit/phpunit
```

- بعد از تغییر CSS، مرورگر را با Ctrl+F5 تازه کنید.
- خطای could not find driver: افزونهٔ pdo_sqlite را در PHP فعال کنید.
- خطای تاریخ شمسی: فعال بودن intl را بررسی کنید.
- خطای اتصال API: دسترسی شبکه را از خود میزبان یا کانتینر Laravel بررسی کنید، نه فقط مرورگر کاربر.
- جزئیات خطاهای Laravel در storage/logs/laravel.log ثبت می‌شود؛ این فایل در Git منتشر نمی‌شود.
- این راهنما برای اجرای محلی است. برای محیط production باید دسترسی کاربران پنل، وب‌سرور و APP_DEBUG=false را جداگانه تنظیم کنید؛ مدل فعلی User برای پنل محلی آماده شده است.

## ساختار اصلی

- app/Services/SystemMonitor.php: ارتباط HTTP، کش و آماده‌سازی داده‌های API.
- config/system-monitor.php: خواندن تنظیمات از .env.
- app/Filament/Pages: صفحات سیستم‌ها و سرویس‌ها.
- app/Filament/Widgets: کارت‌ها، جدول‌ها، نمودارها و عملیات کانتینر.
- app/Support: قالب‌بندی مقادیر، تاریخ شمسی و واسط رکوردهای API برای جدول Filament.
- lang/fa/monitoring.php: متن‌های قابل تغییر پنل.
- public/css/monitoring-layout.css: اصلاح چیدمان محدود به صفحهٔ سرویس‌ها.

## مانیتورینگ سرور

آدرس سرویس در `.env` با `SYSTEM_MONITOR_URL` تنظیم می‌شود. پس از تغییر آن `php artisan config:clear` را اجرا کنید. این آدرس باید از سیستمی که Laravel روی آن اجرا می‌شود در دسترس باشد.

پنل دو داشبورد مستقل دارد. Swagger در `/docs` مستندات API است. همهٔ دریافت‌ها در Laravel توسط `app/Services/SystemMonitor.php` انجام می‌شوند.

| داشبورد | آدرس | اطلاعات |
| --- | --- | --- |
| سیستم‌ها | `/admin` | CPU، RAM، دیسک، نام و زمان روشن‌بودن میزبان، نمودار تاریخچهٔ مصرف منابع |
| سرویس‌ها | `/admin/services` | سلامت API، تعداد کل/فعال/متوقف کانتینرها، جدول مصرف منابع و ترافیک، تاریخچهٔ سرویس انتخابی، لاگ انتخابی، موجودی Imageها |

API فعلی یک میزبان و کانتینرهای Docker آن را معرفی می‌کند. سرویس‌ها در این پنل همان کانتینرها هستند؛ وضعیت `running` به‌تنهایی سلامت برنامه را تأیید نمی‌کند. این API سلامت مجزای تک‌تک برنامه‌ها را گزارش نمی‌کند.

مسیرهای استفاده‌شده: `/health`، `/api/summary`، `/api/stats`، `/api/containers`، `/api/images`، `/api/metrics/host/history`، `/api/metrics/containers/history` و `/api/containers/{id}/logs`.

جدول سرویس‌ها دکمه‌های «راه‌اندازی» و «توقف» دارد. پس از تأیید نام سرویس در مودال، وضعیت آن از `/api/containers/{id}/stats` دوباره خوانده می‌شود و در صورت معتبر بودن عملیات، درخواست `POST /api/containers/{id}/start` یا `POST /api/containers/{id}/stop` ارسال می‌شود. راه‌اندازی برای وضعیت‌های `created` و `exited` و توقف برای `running`، `restarting` و `paused` فعال است. نتیجه با اعلان نمایش داده می‌شود و کش همان مانیتور و کارت‌های تعداد سرویس‌ها تازه می‌شوند. خطای ارتباط به معنی نامشخص‌بودن نتیجه است؛ دستور به‌صورت خودکار تکرار نمی‌شود.

توقف خود API از پنل ممنوع است: `SYSTEM_MONITOR_PROTECTED_CONTAINERS` فهرست نام‌ها یا شناسه‌های محافظت‌شده با جداکنندهٔ کاماست و مقدار پیش‌فرض آن `system_monitor` است. در استقرار دیگر، نام واقعی کانتینر API و وابستگی‌های ضروری آن را در این تنظیم قرار دهید. این کنترل در رابط و هنگام تأیید عملیات سمت سرور اعمال می‌شود؛ راه‌اندازی کانتینرهای محافظت‌شده، در صورت در دسترس بودن API، مجاز است.

اگر آمار مصرف دریافت نشود، جدول و بررسی وضعیت قبل از عملیات از `/api/containers?all=true` کمک می‌گیرند تا کانتینر متوقف‌شده بدون داشتن آمار CPU/RAM هم قابل راه‌اندازی باشد. در قطع کامل دریافت اطلاعات، نام‌ها و شناسه‌های آخرین دریافت موفق هر صفحه حداکثر یک روز در کش نگهداری می‌شوند؛ وضعیت و مصرف قدیمی به‌عنوان زنده نمایش داده نمی‌شوند و عملیات غیرفعال است. «بررسی مجدد اتصال» فوراً داده‌ها را دوباره درخواست می‌کند.

دکمهٔ «راه‌اندازی مجدد» کنار راه‌اندازی و توقف، برای وضعیت‌های `running` و `exited` فعال است. پس از تأیید کاربر و بررسی مجدد وضعیت، یک درخواست `POST /api/containers/{id}/restart` ارسال می‌شود و کش مانیتور تازه می‌شود. در قطع ارتباط، نتیجه نامشخص اعلام می‌شود و درخواست تکرار خودکار ندارد. محافظت `SYSTEM_MONITOR_PROTECTED_CONTAINERS` برای راه‌اندازی مجدد نیز اعمال می‌شود تا API مدیریت از داخل خودش ری‌استارت نشود.

اگر خود کانتینر API متوقف شده باشد، ابتدا روی میزبان داکر با `docker ps -a` نام و وضعیت آن را بررسی کنید و با `docker start CONTAINER_NAME` آن را روشن کنید. این کار از طریق API خاموش‌شده ممکن نیست و باید توسط مدیر همان میزبان انجام شود.

جدول کانتینرها و Imageها صفحه‌بندی ۱۰تایی دارند. نمودار میزبان آخرین ۶۰ رکورد را نشان می‌دهد. نمودار سرویس برای هر روز بازه یک تاریخ شمسی و میانگین CPU و RAM همان روز را نشان می‌دهد؛ مثلاً بازهٔ ۱۰روزه دقیقاً ۱۰ تاریخ دارد. میانگین از همهٔ نمونه‌های معتبر دریافت‌شدهٔ آن روز محاسبه می‌شود، نه میانگین میانگینِ صفحات یا فقط ۶۰ رکورد آخر. مقادیر نامعتبر از محاسبهٔ همان شاخص حذف می‌شوند؛ صفر معتبر باقی می‌ماند و روز بدون داده خالی است. میانگین امروز تا آخرین نمونهٔ دریافت‌شده است. تاریخ ثبت‌شدهٔ API حفظ می‌شود؛ چون تاریخچه منطقهٔ زمانی مشخصی ندارد، تبدیل حدسی منطقهٔ زمانی انجام نمی‌شود. انتخابگر نمودار سرویس تا ۵۰۰ کانتینر اول را پوشش می‌دهد. لاگ فقط پس از انتخاب کاربر و در صفحات ۵۰خطی خوانده می‌شود؛ API حداکثر ۲۰هزار خط را پشتیبانی می‌کند.

ویجت‌های سیستم هر ۱۰ ثانیه و ویجت‌های سرویس هر ۳۰ ثانیه در صفحهٔ باز تازه می‌شوند؛ لاگ تازه‌سازی دستی دارد. پاسخ‌های خام برای ۱۰ ثانیه و نتیجهٔ تجمیع روزانه برای ۳۰ ثانیه کش می‌شوند. هر درخواست HTTP حداکثر ۸ ثانیه فرصت پاسخ دارد. دادهٔ نامعتبر یا خطای ارتباط با وضعیت عدم دسترسی نمایش داده می‌شود. تاریخچهٔ خالی از خطای دریافت تفکیک شده است. ساعت «آخرین بررسی» بر اساس تهران است.

مقدار RAM با واحد MB و دیسک با واحد GB مطابق پاسخ API نمایش داده می‌شود.

CPU کانتینر روی چند هسته ممکن است از ۱۰۰٪ بیشتر شود. اعداد شبکه و Block I/O تجمعی‌اند، نه نرخ انتقال بر ثانیه. اندازهٔ Imageها الزاماً فضای دیسک قابل آزادسازی نیست، چون لایه‌ها می‌توانند مشترک باشند.

دکمهٔ «نمایش لاگ» مودال شامل نام، شناسه و لاگ همان سرویس را باز می‌کند. ویجت `ContainerLogs` داخل `ContainerMetrics` قرار دارد و نیازی به ثبت جداگانهٔ آن در داشبورد نیست. مودال صفحه‌بندی، حالت دریافت اطلاعات، خطا و لاگ خالی دارد. «تازه‌سازی لاگ» کش همان صفحه را تازه می‌کند تا تلاش مجدد بلافاصله درخواست جدید بفرستد.

صفحه‌بندی لاگ از دکمه‌های قبلی و بعدی خود Filament استفاده می‌کند. دکمهٔ شمارهٔ صفحه نیز یک انتخابگر برای صفحات کشف‌شده باز می‌کند؛ API تعداد کل صفحات را نمی‌دهد. حداکثر ۴۰۰ صفحهٔ ۵۰خطی قابل دسترسی است. با باز شدن مودال برای یک سرویس، صفحه از ۱ شروع می‌شود.

مودال لاگ جست‌وجوی فوری در همان صفحهٔ بازشده دارد؛ حروف کوچک و بزرگ تفاوتی ندارند. دکمهٔ «کپی لاگ‌های نمایش‌داده‌شده» متن خام خطوط مطابق جست‌وجو را، بدون شمارهٔ ردیف و قالب HTML، کپی می‌کند. بدون جست‌وجو تمام خطوط همان صفحه کپی می‌شوند. در HTTP شبکهٔ داخلی، اگر Clipboard API در دسترس نباشد از روش انتخاب متن استفاده می‌شود؛ شکست کپی پیام مشخص دارد. شمارهٔ خطوط، رنگ متفاوت خطا و هشدار و انتخاب شکستن خطوط بلند به خوانایی کمک می‌کنند. جست‌وجو فقط روی صفحهٔ دریافت‌شده است و هنگام رفتن به صفحهٔ دیگر حفظ می‌شود؛ پاسخ‌های API همچنان کش می‌شوند و لاگ به‌صورت متن escape‌شده نمایش داده می‌شود.

## کامپوننت‌های اصلی Filament

تمام کارت‌ها از StatsOverviewWidget و Stat، جدول کانتینرها و Imageها و لاگ از TableWidget، و نمودارها از ChartWidget استفاده می‌کنند. ستون‌ها TextColumn هستند؛ دکمه‌ها، مودال‌ها، اعلان‌ها، جست‌وجو و صفحه‌بندی از خود Filament می‌آیند. جدول‌ها و کارت‌ها از قالب‌های اصلی Filament استفاده می‌کنند. قالب نمودار سرویس نسخهٔ قالب اصلی ChartWidget است که فقط اکشن‌های بازه به headerEnd آن اضافه شده‌اند؛ ظاهر، نمودار، ورودی‌ها و مودال‌ها همچنان کامپوننت‌های Filament هستند. ظاهر کامپوننت‌ها با تم پنل مقصد تعیین می‌شود؛ فایل کوچک public/css/monitoring-layout.css فقط چیدمان کارت‌ها و کادر نمودار صفحهٔ سرویس‌ها را اصلاح می‌کند.

تنها استثنا، تقویم شمسی قبلی است که با تأیید کاربر حفظ شده است: app/Filament/Forms/JalaliDatePicker.php یک فیلد فرم Filament است و resources/views/filament/forms/jalali-date-picker.blade.php فقط رابط تقویم آن را پیاده می‌کند. تبدیل تاریخ همچنان در app/Support/JalaliDate.php و با افزونهٔ intl انجام می‌شود؛ تقویم از Alpine همراه Filament و Intl مرورگر استفاده می‌کند.

Filament 3 برای ستون‌ها و اکشن‌های جدول، رکورد مدل می‌خواهد. app/Support/MonitorRecord.php فقط یک واسط در حافظه برای آرایه‌های API است. PaginatedMonitorWidget رکوردها و صفحه‌بندی را از پاسخ API تأمین می‌کند و برای انتخاب رکورد اکشن نیز همان داده‌ها را می‌خواند. هیچ جدول دیتابیس، migration یا کپی دادهٔ API به دیتابیس ایجاد نشده است. روی این جدول‌ها نباید بدون پیاده‌سازی سمت API، مرتب‌سازی یا جست‌وجوی SQL اضافه شود. جست‌وجوی لاگ روی خطوط همان صفحه در حافظه انجام می‌شود.

### بازهٔ زمانی

در سربرگ خود ویجت «تاریخچهٔ مصرف منابع سرویس» یک ActionGroup استاندارد با گزینه‌های امروز، دیروز، ۵ روز اخیر، هفتهٔ اخیر، ماه اخیر و بازهٔ دلخواه قرار دارد. متن دکمه نام بازهٔ انتخاب‌شده است. «بازهٔ دلخواه» یک مودال فرم استاندارد با دو تقویم شمسی باز می‌کند؛ امکان تایپ تاریخ هم حفظ شده است. بازهٔ معتبر مستقیماً در همان ویجت اعمال می‌شود و تاریخ دقیق در توضیح نمودار دیده می‌شود.

پیش‌فرض امروز به وقت تهران و چهار روز قبل است. هفته و ماه اخیر، ۷ و ۳۰ روز منتهی به امروز هستند. بازهٔ یک‌روزه ۲۴ نقطهٔ ساعتی و بازهٔ چندروزه یک نقطه برای میانگین هر روز دارد. ابتدا و انتهای بازه کامل محاسبه می‌شوند و حداکثر بازه ۳۶۶ روز است. تاریخ نامعتبر، بازهٔ قبلی را عوض نمی‌کند.

API فعلی تاریخچه فیلتر تاریخ یا تجمیع ندارد. سرویس با پارامترهای container_id، page و page_size رکوردها را می‌خواند و در PHP تجمیع می‌کند. ابتدا سقف ۱۰۰ صفحهٔ ۵۰۰تایی بررسی می‌شود؛ در صورت ناقص بودن، دکمهٔ استاندارد «بررسی صفحات بیشتر» در سربرگ همان ویجت ظاهر می‌شود و سقف را تا ۱۰۰۰ صفحه افزایش می‌دهد. ساعت یا روزی که نمونه‌هایش کامل دریافت نشده، به‌عنوان میانگین کامل نمایش داده نمی‌شود.

### اصلاح پنج‌ستونه و کادر نمودار، فقط در صفحهٔ سرویس‌ها

StatsOverviewWidget در Filament 3 برای پنج کارت، سه ستون انتخاب می‌کند. قالب اصلی آن فقط ستون‌های ۱ تا ۴ را پشتیبانی می‌کند؛ بنابراین صرفاً برگرداندن ۵ از getColumns کافی نیست.

ServicesDashboard از متد اصلی getExtraBodyAttributes برای افزودن data-monitoring-dashboard="services" به صفحه استفاده می‌کند. تمام قواعد فایل public/css/monitoring-layout.css با همین نشانگر آغاز می‌شوند. کارت‌ها در عرض ۱۰۲۴ پیکسل به بالا پنج ستون مساوی، در تبلت دو ستون و در موبایل یک ستون دارند. رنگ، فونت، padding و آیکون کارت‌ها از تم موجود می‌آیند. صفحهٔ سیستم‌ها و بقیهٔ صفحات تحت تأثیر این قواعد نیستند.

نمودار همین صفحه پس‌زمینه، حاشیه و گوشه‌های گرد می‌گیرد. رنگ روشن پیش‌فرض سفید و رنگ تاریک پیش‌فرض خاکستری تیره است. برای تطبیق دقیق با تم شرکت، متغیرهای monitoring-chart-background، monitoring-chart-border، monitoring-chart-radius و monitoring-chart-shadow را در CSS با پیشوند -- تعریف کنید؛ برای رنگ و حاشیهٔ حالت تاریک نیز متغیرهای monitoring-chart-dark-background و monitoring-chart-dark-border وجود دارند. قواعد تم شرکت در این پروژه موجود نیستند، بنابراین این مقادیر، پیش‌فرض بازگرداندن کادر هستند.

اگر نسخهٔ قبلیِ بازنویسی با کامپوننت‌های اصلی را منتقل کرده‌اید، برای این اصلاح فقط:

1. فایل public/css/monitoring-layout.css را کپی کنید.
2. متد زیر را به ServicesDashboard مقصد اضافه کنید؛ اگر متد مشابهی دارید، نشانگر را در خروجی همان متد ادغام کنید:

~~~php
public function getExtraBodyAttributes(): array
{
    return [...parent::getExtraBodyAttributes(), 'data-monitoring-dashboard' => 'services'];
}
~~~

3. در Provider پنل، فایل CSS را کنار دارایی‌های فعلی ثبت کنید؛ کل Provider یا assets موجود را جایگزین نکنید:

~~~php
use Filament\Support\Assets\Css;

// Add alongside the panel's existing configuration:
->assets([
    Css::make(
        'monitoring-layout',
        asset('css/monitoring-layout.css').'?v='.filemtime(public_path('css/monitoring-layout.css')),
    ),
])
~~~

در پروژهٔ حاضر این ثبت در AdminPanelProvider انجام شده است. پس از انتقال، view:clear و سپس Ctrl+F5 را اجرا کنید. به تغییر ویجت‌ها، API، نصب پکیج یا build این فایل CSS نیاز نیست.

### انتقال کامل بازنویسی به پروژهٔ شرکت که قبلاً مانیتورینگ دارد

فایل‌های زیر را به‌روز یا اضافه کنید:

- app/Filament/Pages/ServicesDashboard.php
- app/Filament/Widgets/DashboardStats.php
- app/Filament/Widgets/ServiceStats.php
- app/Filament/Widgets/PaginatedMonitorWidget.php
- app/Filament/Widgets/ContainerMetrics.php
- app/Filament/Widgets/ContainerLogs.php
- app/Filament/Widgets/ImageInventory.php
- app/Filament/Widgets/ContainerHistoryChart.php
- resources/views/filament/widgets/container-history-chart.blade.php (قالب اصلی نمودار با اکشن‌های سربرگ)
- app/Support/MonitorRecord.php (جدید)
- app/Filament/Forms/JalaliDatePicker.php (جدید)
- resources/views/filament/forms/jalali-date-picker.blade.php (جدید)
- public/css/monitoring-layout.css (اصلاح محدود به صفحهٔ سرویس‌ها)

وابستگی‌های قبلی یعنی SystemMonitor.php، MonitorFormat.php، JalaliDate.php، config/system-monitor.php، lang/fa/monitoring.php، SystemDashboard.php و HostHistoryChart.php همچنان لازم‌اند؛ در این بازنویسی تغییر نکرده‌اند. URL و تنظیمات .env شرکت را حفظ کنید.

در Provider شرکت فقط ثبت CSS قدیمی مانیتورینگ را حذف کنید (widget-card-theme یا monitoring-widgets). **کل Provider یا فایل theme.css اصلی شرکت را جایگزین یا حذف نکنید.** اگر قواعد .monitor-* یا قواعد مانیتورینگ با :has(...) را در تم اصلی ادغام کرده بودید، فقط همان بخش‌ها را بردارید. ثبت صفحات و تم اصلی پروژه حفظ شود. در پروژهٔ حاضر ثبت CSS قدیمی از AdminPanelProvider حذف شده است. ثبت جدید monitoring-layout مربوط به اصلاح محدود بالا است و باید مطابق همان راهنما اضافه شود.

قالب‌های قدیمی زیر دیگر استفاده نمی‌شوند و از پروژهٔ حاضر حذف شده‌اند؛ نسخهٔ مقصد آن‌ها را نیز می‌توانید حذف کنید:

- resources/views/filament/widgets/monitor-stat-cards.blade.php
- resources/views/filament/widgets/container-metrics.blade.php
- resources/views/filament/widgets/container-logs.blade.php
- resources/views/filament/widgets/image-inventory.blade.php
- resources/views/filament/widgets/monitor-pagination.blade.php
- resources/views/filament/widgets/jalali-date-input.blade.php (به فیلد فرم بالا منتقل شده)

بعد از انتقال:

~~~shell
php artisan view:clear
php artisan filament:clear-cached-components
~~~

سپس مرورگر را با Ctrl+F5 تازه کنید. به نصب composer/npm، اینترنت، migration یا build جدید برای خود این تغییرات نیاز نیست. نسخهٔ مقصد باید Filament 3 سازگار و دارایی‌های معمول همان پنل را داشته باشد. اگر تم سفارشی شرکت قوانین عمومی جدول‌ها یا ویجت‌های Filament را تغییر می‌دهد، این ویجت‌ها هم همان قوانین را می‌گیرند.

متن‌های اختصاصی مانیتورینگ در lang/fa/monitoring.php قابل ویرایش‌اند. متن‌های عمومی کامپوننت‌ها، مانند صفحه‌بندی و عنوان پیش‌فرض جست‌وجو، از ترجمه‌های خود Filament می‌آیند.

### بررسی

تست‌ها از HTTP fake استفاده می‌کنند و هیچ عملیات واقعی روی کانتینرها انجام نمی‌دهند:

~~~shell
php vendor/phpunit/phpunit/phpunit
~~~

پوشش شامل داده‌های کارت‌ها، قالب‌های اصلی Filament، صفحه‌بندی API بدون کوئری SQL، مودال لاگ و جست‌وجو/کپی متن، محافظت عملیات کانتینرها، خطا و بازیابی اتصال، و تقویم و میانگین‌های ساعتی/روزانه است.
### انتقال فیلتر بازه به داخل ویجت تاریخچه

برای نسخه‌ای که فیلتر آن قبلاً بالای صفحه بوده، فقط این سه فایل را به‌روز کنید:

- app/Filament/Pages/ServicesDashboard.php — اکشن‌ها و وضعیت بازه از صفحه حذف شده‌اند؛ نشانگر CSS صفحه حفظ شده است.
- app/Filament/Widgets/ContainerHistoryChart.php — اکشن‌ها، فرم تقویم و انتخاب بازه داخل خود ویجت هستند.
- resources/views/filament/widgets/container-history-chart.blade.php — از قالب اصلی Filament 3 گرفته شده و فقط کنترل‌های استاندارد به سربرگ آن اضافه شده‌اند. جدول یا طراحی اختصاصی جدیدی ندارد.

تقویم JalaliDatePicker و فایل Blade آن که قبلاً منتقل شده‌اند همچنان لازم‌اند و تغییر نکرده‌اند. CSS، API، کانفیگ و ترجمه تغییری ندارند. در صفحهٔ مقصد اگر مسیر یا تنظیمات اختصاصی دارید، آن‌ها را حفظ کنید؛ قسمت‌های getHeaderActions، historyRangeLabel، historyDates، historyCanLoadMore و historyPagination مربوط به فیلتر قدیمی باید از ServicesDashboard حذف شوند.

پس از انتقال، php artisan view:clear و سپس Ctrl+F5 را اجرا کنید.
